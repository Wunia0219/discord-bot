2026-10-31 已啟用精簡結算，保留 Firestore v2、原 namespace／帳本 ID 與[停輪基準](reel-timing-baseline.md)，現行產品為 1.0.1。策略由原 meta 的 `compactSettlements` 明確控制；部署相容讀取程式不會改寫歷史。啟用時原 nextId 為 1555，P/R 從後續新操作開始，不回編舊資料。發布與驗證紀錄集中於[正式服交付](customer-handoff.md)。

## 每局文件與交易

| 一般既有玩家的一局 | 原格式 | 精簡格式 |
| --- | ---: | ---: |
| 同一交易內批次讀取 | 4 | 4 |
| 原子提交文件寫入 | 6 | 4 |
| 每局新增永久文件 | 3 | 2 |
| 增量備份該局的讀取 | 3 | 2 |

精簡格式保留根帳本、meta、錢包、原請求收據四份文件。收據內原有的完整結果成為該局權威結果，新增單欄位 `roundKey` 索引，省去重複的 `wallets/.../rounds/...` 文件。近期 100 局的無損壓縮快取保留；較舊查詢合併新收據與舊 round 文件，保留原序號、游標及完整歷史。舊 round 文件不刪除、不重編。

當日摘要併入原本就會寫入的錢包 `pendingDay`，同筆交易內更新；換日時另寫一次前一天摘要。日期倒退也先保存離開的日期，再載入目標日期，避免覆蓋已保存的總數。期間摘要使用唯讀一致快照，將 pending day 覆蓋同日舊摘要，不重複加總。這不是延後餘額或結果入帳。

跨日第一局多 1 寫；新錢包的新手入帳多 1 寫；需要得獎公告的局數另多 1 寫。簽到、發獎、登入、重設、重試及背景維護另計。仍在同一個原子交易裡保存餘額、帳本及請求去重；相同請求重送不再寫入、下注不同則拒絕。未知提交結果不能換新 request ID 重送。

## 編號

- 新遊玩結果使用 `P000001` 起的獨立系列；發獎與收回使用 `R000001` 起的另一系列，跨群共用同一 meta 的系列計數。
- 計數沿用同一筆 meta 寫入；編號放在既有收據及帳本索引，沒有新增每局編號對照文件。
- 管理面板顯示 R 編號，按鈕及更正接受新 R 編號與舊數字 ID；跨群更正、重複收回、權限及餘額檢查保留。舊紀錄保留原 `#數字`。
- 底層帳本仍使用原本連續 ID，供排序、分頁、備份檢查與重設範圍使用；沒有將既有財務關聯改成顯示編號。
- 完整備份保存原收據及 P/R 編號。還原匯入會驗證編號並從最大值恢復兩個計數器，避免重新從 1 編號。

分開編號讓發獎容易查核；減少重複永久文件才會降低資料樹的成長速度。此方案仍保留完整帳本，資料量不會變成固定大小。

## Cloudflare 額度記帳

Firestore REST 交易在送出 commit 前，一次預留所有寫入額度。文件大小與各 scope 的限制仍逐一檢查，整批原子記帳；失敗或未知提交不退回預留。明確 ABORTED 的下一次嘗試另外預留。SDK 介面沒有提交 hook 時維持原逐筆預留。

同批讀取的傳輸估算合併一次紀錄，寫入額度與儲存成長各批次更新一次，但每份文件的最大成長仍分別保存。這降低額度記帳本身的 SQLite 寫入，不折減既有用量，也不改成低估 Firestore 嘗試次數。

文件大小的新紀錄寫入 `quota_document_sizes`（`WITHOUT ROWID`），省去重複主鍵索引。舊 `quota_documents` 留在原處；查詢與匯出對相同 scope／key 取兩表最大值，沿用原成長總額，不重計歷史。升級只建立空表，隔離 workerd 測得一次性 2 列系統寫入，之後重啟為 0；沒有隨歷史筆數增加的搬移成本。匯出格式不變，移入直接使用新表，拒絕覆寫已有紀錄。

相同四份文件、8 單位寫入預留與 1,600 bytes 成長，隔離 workerd 的逐筆／整批處理現為 **13／7 rows written**；先前 rowid 格式為 17／11。完整前景結算比較見[Cloudflare 費用](cloudflare-costs.md)，不能將這個局部比例當成整個遊戲的降幅。

發布後需回退時保留能讀取兩表的 `cloud/quota.js`，或先透過既有停機移交程序匯出合併紀錄，再交回舊服務；不能直接回退只讀舊表的 Worker，否則會重複估算新表紀錄的成長。Firestore 帳本、收據與結算格式不受此表格調整影響。

維運的 80% 提醒是「內部保守預留估算」，不是 Google 帳單：讀取保留每文件 6 次、寫入 2 次的容錯預留，包含失敗嘗試；讀寫窗口為滾動 24 小時。Firebase 每日免費用量則約在太平洋時間午夜重設。兩者不能直接當成相同百分比。

## 費用情境（2026-10-31）

依 [Firestore 官方價格](https://cloud.google.com/firestore/pricing) 中 **Taiwan (asia-east1)、Default USD、Monthly**，超額讀取 US$0.0345／10 萬份、寫入 US$0.1042／10 萬份；每日免費讀取 50,000、寫入 20,000。試算以 30 天、每天均勻遊玩，原格式每局 6 寫／7 讀、精簡後 4 寫／6 讀，包含每局增量備份讀取。

| 全體每天局數 | 原格式每月讀寫費 USD | 精簡後每月讀寫費 USD |
| --- | ---: | ---: |
| 1,000 | 0.00 | 0.00 |
| 10,000 | 1.46 | 0.73 |
| 100,000 | 24.86 | 17.57 |

每日費用公式：`max(讀取數−50000,0)×0.0345/100000 + max(寫入數−20000,0)×0.1042/100000`，再乘 30。這是文件讀寫部分，不是整體帳單；不含額外操作、重試、跨日摘要、備份頁面固定成本、儲存及索引、傳出流量、Cloudflare 與稅金。儲存另有 1 GiB 免費，台灣區超額 US$0.1725／GiB 月；實際索引與傳輸量以供應商帳單為準。

Firebase 圖片中的 600,000 寫、1,500,000 讀是月試算器對 30 天的換算，不是可任意跨日挪用的免費池。每日 20,000 寫／50,000 讀沒有用完，不會留給隔天。Blaze 已允許超額計費，應用程式維持 notify-only。

Cloudflare SQLite 列數包含索引、登入、額度記帳及背景工作，不等於 Firestore 文件數；供應商硬上限及合併成本模型見[Cloudflare 費用](cloudflare-costs.md)。

## 啟用與回復

先完整驗證並部署具備新舊格式讀取、備份、還原相容性的版本，保留該版本 ID，再執行：

```powershell
node scripts/admin/cloud-control.js settlement-policy --env .env.cloud.production.local --compact true
```

此操作只在原 meta 上啟用新寫入策略，不清空、不重新 seed、不更換 namespace，也不降低既有 nextId 或額度。須使用管理員 token；monitor token 只能讀取摘要。

需要回復寫入策略時使用 `--compact false`。相容版本仍讀取精簡歷史與 pending day，保留 P/R 計數；新局改回原布局。**啟用過精簡寫入後，不可退回不懂新格式的舊程式。** 最早已發布相容 Worker 為 `ed978184-955e-46fa-a231-98d29fa87cd6`；回復策略或相容版本，避免漏讀歷史與摘要。
