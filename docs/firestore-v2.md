後續真實備份、還原演練、額度阻擋及自動接續狀態見 [遷移進度](firestore-v2-migration-status.md)。本頁下方的原始測試數字保留為開發階段紀錄。

## 結果

同一份含 105 局的 SQLite 快照分別匯入 v1／v2，再以相同停點、下注、時間及回合 ID 結算一局；無 SDK／交易重試。完整結果會由 `npm run test:firestore` 重建於 `test-results/spark-v2-metrics.json`。

| 項目 | v1 | v2 | 改善 |
|---|---:|---:|---:|
| 每局文件寫入 | 10 | 6 | 減少 40% |
| 每局讀取 JSON | 56,879 bytes | 12,238 bytes | 減少 78.5% |
| 每局寫入 JSON（含查詢欄位） | 69,684 bytes | 14,317 bytes | 減少 79.5% |
| 結算 HTTP JSON 回應 | 57,030 bytes | 760 bytes | 減少 98.7% |
| 錢包 JSON | 56,593 bytes | 11,960 bytes | 減少 78.9% |
| 冷登入＋最近 100 局的雲端文件讀取 | 1 | 1 | 保持不變 |
| 同一份樣本的移入文件數 | 762 | 326 | 減少 57.2% |

這是測試情境的 JSON 大小，不是 Google 帳單或封包實測；HTTP／gRPC、Google 索引儲存及傳輸壓縮另計。樣本中的舊回合使用隨機停點，重跑時 byte 數會略變，測試要求各項內容大小至少降低 70%。一般旋轉仍讀取 4 份文件，保守預留為讀 24／寫 12；相同 15,000 寫入預算的純旋轉理論上限由 750 提升到 1,250 局，簽到、首次帳號、管理操作、重試、備份及其他門檻會降低可用容量。

## 如何保留完整資料

每局仍在一筆 Firestore 交易內寫入六份文件：根帳本、metadata、錢包、每日摘要、完整回合、原請求結果。取消的四份玩家分類／每日流水副本，由根帳本上的 `ownerKey`、`categoryKey`、`dayKey`、`categoryDayKey` 取代。每個鍵包含完整群、玩家與補零的帳本序號，查詢只對一個欄位作範圍及排序，避免跨玩家混入或數字字串排序錯誤。

這些查詢使用 Firestore 預設單欄位索引，不新增複合索引；如果專案曾停用這些欄位的預設索引，採用前須恢復並驗證查詢。單一範圍欄位免索引項目讀取費用的規則見 [官方計費](https://firebase.google.com/docs/firestore/pricing)，索引支援見 [官方索引說明](https://firebase.google.com/docs/firestore/query-data/index-overview)。

錢包保留 `historyRevision` 與最近 100 局的 **無損壓縮快取** `historyCache`。格式為帶版本的 DEFLATE＋Base64，解壓後是原回合及其帳本序號；未知／舊版欄位、中文與數值全部保留，解壓限制為 2 MiB。完整回合與原請求結果仍獨立永久保存，不從停點重新算獎，也不縮短去重期限。

保留壓縮快取是為了讓冷登入仍只讀一份錢包：若完全拆開，最近 100 局會額外消耗約 100 次文件讀取。快取窗口內的歷史同步由後端已讀取的錢包解壓提供；更舊的頁面或超出快取覆蓋範圍的同步，才讀取獨立回合文件。

## 前端與 API 相容

- 新 client 以 `X-Wallet-View: compact-v1` 要求輕量狀態。一般輪詢回傳餘額、簽到、revision 等，不重傳 100 局；新旋轉回傳本局與歷史前後版本。
- 同一裝置連續旋轉直接合併本局；跨裝置、重新整理或漏回應時，透過 `/api/rounds?after=…&through=…&limit=100` 補齊。`through` 固定到該錢包快照的歷史版本，避免較新的回合配上較舊餘額。
- 慢回應不能覆蓋已知的新 revision。歷史補齊失敗時仍保留原旋轉請求，重新開頁後也不換新 ID 重扣。
- 玩家先看到最近 100 局；v2 提供「載入更早的紀錄」，每頁最多 50 局，失敗可重試原頁。沒有額外收支金額或技術欄位顯示給玩家。
- 舊 client 沒有傳新標頭時仍收到完整快照；v1／SQLite 仍使用原完整快照。只升級前端不會破壞舊服務，但六次寫入與壓縮收益須完成 v2 資料切換才生效。
- 新回合 API 沿用登入、群與玩家隔離、HTTP 方法與本機測試保護；游標及頁大小會驗證。歷史查詢不能修改餘額。

## 遷移：只匯入新的空白命名空間

`FIRESTORE_SCHEMA_VERSION` 是後端設定，預設仍為 `1`。設定 `2` 時只能讀寫 metadata 版本 2；v1 程式／設定連上 v2 或反向都會拒絕啟動。不要把既有 namespace 原地改成 v2；也不要只修改 metadata 的版本數字。

1. 安排切換時段，停止舊入口的新寫入，保留一份最新且驗帳成功的完整邏輯快照。來源停止到取得快照、驗證目標及切換完成期間，都不得再有舊端寫入，避免漏掉切換後的新進度。
2. 在獨立後端環境設定檔選擇新的同環境 namespace，例如 `jokers-circus-v2-test`，設定 `FIRESTORE_SCHEMA_VERSION=2`。沿用原專案及原 `FIRESTORE_QUOTA_PATH`，不清空或複製出另一份獨立額度。
3. 先執行純本機規劃。以下 `C:/secure/v2.env` 與快照路徑須換成實際的隔離設定／已驗證快照：

   ```powershell
   node --env-file=C:/secure/v2.env scripts/admin/import-firestore.js --from C:/backups/latest.sqlite --dry-run
   ```

   只輸出目標、結構版本、文件數、指紋及讀寫預留估算，不連 Firestore 或開啟額度檔。此步不證明雲端 namespace 空白，也不代表剩餘額度足夠。
4. 檢查總額度足以容納完整移入與逐份驗證後，移除 `--dry-run` 執行。原始回合、帳本 ID、請求結果、管理更正及每日摘要不改寫。每批資料與進度原子提交；中斷時維持 `importing`，以同一份來源及同一設定重跑可接續。環境／結構不符或已有玩家的目標會拒絕。
5. 全部 JSON 與查詢欄位逐份讀回驗證後才標示 ready。設定 `FIRESTORE_BACKUP_BASELINE` 指向本次來源快照，並讓遊戲、維護 worker 及管理腳本都使用相同的 v2 設定。先驗收餘額、近期／舊紀錄、摘要、舊旋轉請求去重、簽到及跨裝置，再切換入口。

目前的 `npm run firestore:migrate` 仍讀 `.env.firestore.local`；只有確認其內容指向正確目標時才使用。`firestore:backup`／`firestore:operations` 讀 `.env.server.local`，切換時需同步設定，避免工具與遊戲連到不同 namespace。遊戲版本不用因此遞增。

## 備份與回退

v2 自動備份仍從權威帳本、原請求及原回合建立完整 SQLite 快照；依結構版本重建錢包與壓縮快取並逐項比對，全部通過才發布。備份不需保存四份已移除的查詢副本，因為還原工具會依指定版本重建查詢欄位／副本。

在 v2 尚未接受任何新寫入前，可回到保留的舊入口。**v2 已產生新進度後，不能直接切回舊 namespace**：先停止 v2 新寫入，取得並驗證最新 v2 完整快照，再用 `FIRESTORE_SCHEMA_VERSION=1` 匯入另一個空白 v1 namespace，驗收後切換。這條路徑已用模擬器驗證，包含切換後的新回合、原始舊請求重送及管理更正。

## 測試證據與限制

- 一般回歸：302 項通過，含壓縮無損／解壓上限、索引鍵順序與隔離、原始資料規劃、純本機 dry-run、同步競爭與失敗重送。
- Firestore 官方模擬器：38 項通過，另 1 項需指定真實快照的選用測試跳過。涵蓋 v1 舊路徑、v2 六次寫入、低於 30% 的內容大小、冷登入一讀、跨裝置、舊請求、額度中途耗盡、斷點移入、遷移競爭保護、備份及 v2→v1／v2 還原。
- 正式建置通過；既有大於 500 kB 的 bundle 提示仍存在。
- 本機瀏覽器使用獨立記憶體資料驗證實際遊戲介面：最近 100 局、載入剩餘 5 局、顯示完整 105 局及到尾提示。證據為 `test-results/spark-v2-history.png`；此 UI 驗收未連真實 Firestore。

原始輸出為 `test-results/spark-v2-unit.log`、`spark-v2-firestore.log`、`spark-v2-build.log` 與 `spark-v2-metrics.json`。模擬器不能取代真實專案的 IAM／索引設定、實際網路延遲或真人 Discord 雙裝置驗收。本輪未移入真實雲端、未重啟原服務、未推送或部署。
