# 玩家戲籌與整群重設

本次新增 `/戲籌管理 玩家戲籌` 與 `/戲籌管理 重設戲籌`，沿用管理員／指定戲籌管理身分組檢查及私密回覆。對象為目前伺服器所有已建立錢包的玩家，包括只有簽到及餘額為零的玩家；不另外建立管理員或未參與成員的錢包。

## 指令

- `/戲籌管理 玩家戲籌`：每頁 20 位，顯示目前餘額與累積局數。下一頁填回覆提供的「起始玩家」。查詢不改變資料，Firestore 使用文件 ID 的伺服器前綴範圍及原有單欄索引，直接讀錢包，不掃描遊玩歷史或 Discord 全體成員。
- `/戲籌管理 重設戲籌 確認:True`：原子重設本群全部現有錢包為 10,000，完成後立刻列出每人的實際重設前餘額及重設餘額。保留週簽到、全部回合、摘要、里程碑及開轉冷卻。未確認不執行。
- `/戲籌管理 重設戲籌 紀錄編號:<原回覆編號> 頁碼:2`：讀取同一份不可變報表，每頁 20 位；即使同時填確認，也只查詢，不再重設。重複送達同一個 Discord interaction ID 同樣只回傳原結果。重新輸入且確認的新指令會執行新一筆重設。

玩家戲籌是查詢當下的資訊。重設不採用先前查詢結果，而是在同一筆交易內重新讀取全部權威錢包、寫入 10,000 與保存原餘額。開轉、簽到、發放與新錢包建立共用既有 metadata，與重設交易序列化；SQLite 使用 BEGIN IMMEDIATE。重設前已結算的回合納入原餘額，重設後結算的回合從新餘額開始。尚未完成的動畫可能仍顯示上一局，其已提交結算不會再入帳；原請求重送只回傳舊回合及最新錢包。

## 保存、成本與容量

每次重設只新增一份 `operations` 結果 `reset:<interaction ID>`，含操作者、時點、每人 before/after、總額及人數；每位玩家新增一筆 `ledger.kind=reset`，包含已是 10,000 的玩家。帳本內保留 delta 供連續性驗帳，玩家與管理員介面不把重設顯示為一般加減款，而是「餘額重設／重設後餘額 10,000」。不刪除資料，也不重寫舊回合。

Firestore v2 的重設交易讀取 metadata、去重結果及 N 份錢包，寫入 `2N+2` 份文件（N 錢包、N 帳本、metadata、單份結果）；v1 沿用四份查帳副本，為 `6N+2`。供應商及交易重試另計；現行持久額度仍保守預留重試成本。重送原指令為零寫入。錢包同份文件增加一個最近重設標記，不新增正常開轉、簽到或狀態查詢的雲端讀寫次數，不增加輪詢或排程。

本版以「全部成功或全部不變」為優先，SQLite／Firestore v2 單群單次上限 **100 份錢包**，v1 **60 份**；Firestore 另在寫入前以估算 6 MiB 限制交易資料量。超出時整筆拒絕，不分段重設、不略過玩家。這不是可無限擴充的設計；正式營運規模超出前，須設計受控維護／分批結算機制，不能直接提高常數後宣稱仍有相同保證。

SQLite schema 遷移至 3，只增加最近重設的部分索引，七份備份資料表不變。產品版本維持 0.2.8。畫面保留最近一次重設標記，完整多次重設及回合仍在帳本；最近 100 局是畫面快取，並非完整保存上限。歷史較長時先顯示明確的最近重設摘要，載入相應舊回合後移到正確時間位置；以前一局 ID 定位，避免毫秒相同時排錯。

## 備份與驗證

SQLite、完整與增量 Firestore 備份、Worker 分段快照及 v1／v2 匯入都保留批次原結果。只有該批第一筆帳本連結原操作，其餘明確為 null，跨 20 筆 checkpoint 不重複保存同一份報表；驗帳要求每筆重設都屬於該批結果且金額連續。還原從原帳本與操作重建最近重設標記，重送舊重設不會覆蓋還原後的新遊玩。

新增驗證涵蓋本群隔離、零餘額與簽到玩家、重送去重、權限、原子失敗回滾、跨服務併發、簽到與歷史保留、REST／SDK 相容及跨分段備份還原。正常／快停參數及產品版本均不調整。此文件描述原始碼行為，不表示已部署、註冊 Discord 新指令或對正式玩家執行重設。
